# 001 — 兩人記帳 LINE Bot 產品規格

狀態：Draft v2

最後產品決策：2026-08-13

時區：Asia/Taipei
幣別：TWD

這份規格是可修改的第一版。若試用結果與假設不同，先修改本文件與驗收案例，再調整實作。

## 1. 產品目標

兩位使用者在專用 LINE 記帳群中，用接近日常說話的方式新增與管理支出：

```text
牛肉麵 150
個人 咖啡 80 #工作
昨天 晚餐 炒麵 80 #約會
```

系統保存金額、日期／時間、付款人、共同或個人歸屬，以及可供統計的多個標籤。每次成功操作都回覆可核對的結果。

## 2. 已確認的產品決策

1. 群組是純記帳群，允許裸格式新增。
2. 系統同時支援共同與個人支出；群組初始為個人模式，約會時可切換共同模式，明確 `共同`／`個人` 前綴只覆蓋該筆。
3. 個人支出在群組內可見，但只有該筆所有人能修改、取消與還原。
4. 不計算誰欠誰，也不做分攤結算。
5. 分類採有類型的多標籤：一個大分類、零或一個餐別、零到多個自訂標籤。
6. 只有正餐型食物會依時間自動推定餐別；咖啡、飲料、點心不自動推定。
7. 補登只有日期、沒有時間時，時間記為未知，也不依訊息送出時間推定餐別。
8. `本月` 顯示不重複總額、共同小計與兩人的個人小計。
9. MVP 做帳目 CRUD；系統分類本身不提供新增、改名或刪除。
10. LINE 原生編輯不自動同步帳目；LINE 收回原始新增訊息時清除該筆帳目內容。

## 3. MVP 範圍

### 3.1 必須完成

- 兩位允許的 LINE 成員新增共同或個人支出。
- 自動分類、餐別推定與自訂標籤。
- 今天、相對日期與明確日期補登。
- 單筆、最近、日／月摘要與標籤篩選查詢。
- 修改一筆帳目的欄位與標籤。
- 軟取消與還原。
- webhook 驗證、依事件型別授權、去重、失敗重試及可觀測的回覆流程。
- 完整稽核，不因 webhook 重送重複建立或修改。

### 3.2 這一版不做

- 收入、預算、週期性帳目。
- 誰欠誰、均分、自訂比例或付款結算。
- 發票 OCR、圖片、檔案或語音記帳。
- 銀行、信用卡或電子支付串接。
- 多幣別與匯率換算。
- 分類／標籤管理後台。
- 真正私密、對另一位群組成員不可見的個人帳。
- LINE 原生編輯訊息自動同步。
- 多帳本公開 SaaS 與完整 Web 後台。
- 使用生成式 AI 決定金額或直接寫入資料庫。

## 4. 帳務語意與權限

### 4.1 共同與個人

| 輸入 | 範圍 | 所有人 | 付款人 |
|---|---|---|---|
| `牛肉麵 150` | 目前模式；初始為個人 | 個人模式時為傳送者 | 傳送者 |
| `共同 牛肉麵 150` | 共同 | 無 | 傳送者 |
| `個人 咖啡 80` | 個人 | 傳送者 | 傳送者 |

付款人與個人所有人是不同概念。例如小明替小美支付一筆小美的個人支出時，可分別設定付款人和所有人。

### 4.2 操作權限

| 操作 | 共同支出 | 個人支出 |
|---|---|---|
| 查看 | 兩人 | 兩人 |
| 修改 | 兩人 | 僅目前所有人 |
| 取消／還原 | 兩人 | 僅目前所有人 |

將個人支出的所有人轉給另一位成員時，只有目前所有人可以執行；成功後權限立即轉移。

`個人` 是帳務歸屬，不是隱私界線。需要真正私密記帳時，必須另做一對一 Bot 流程。

### 4.3 群組記帳模式

- `目前模式`：顯示群組目前是個人或共同模式。
- `切換共同模式`／`共同模式`：後續沒有 scope 前綴的支出預設為共同。
- `切換個人模式`／`個人模式`：後續沒有 scope 前綴的支出預設歸入各傳送者自己的個人支出。
- 模式是 ledger 的持久狀態，兩位 active member 看到並操作同一模式；重啟不重設。
- 明確前綴優先於模式，例如共同模式下的 `個人 咖啡 80`仍是個人，個人模式下的 `共同 晚餐 800`仍是共同。
- 模式只影響新交易，不回溯改變既有交易。

## 5. 標籤模型

使用者看到的分類全部以標籤顯示，但系統保留標籤類型，避免無法可靠統計。

### 5.1 大分類標籤

每筆有效交易恰好一個大分類：

| 代碼 | 顯示名稱 | 關鍵字範例 |
|---|---|---|
| `food` | 食物 | 飯、麵、便當、早餐、午餐、晚餐 |
| `transport` | 交通 | 捷運、公車、計程車、Uber、加油、停車 |
| `entertainment` | 娛樂 | 電影、KTV、遊戲、展覽 |
| `household` | 居家 | 房租、水費、電費、網路、日用品 |
| `shopping` | 購物 | 衣服、鞋、包、網購 |
| `health` | 醫療健康 | 看診、藥、牙醫、健身 |
| `travel` | 旅遊 | 飯店、機票、住宿 |
| `uncategorized` | 未分類 | 無法可靠判斷 |

使用者可用保留標籤明確指定，例如 `牛肉麵 150 #食物`。同時指定兩個不同大分類時拒絕整筆輸入，不任意選一個。

自動分類採最長、最具體規則優先，再比較明確 priority；因此 `飯店` 應先命中旅遊，而不是因 `飯` 命中食物。同順位仍衝突時使用未分類。

### 5.2 餐別標籤

每筆交易最多一個餐別標籤：`早餐`、`午餐`、`下午茶`、`晚餐`、`宵夜`。

自動推定必須同時滿足：

1. 大分類是食物。
2. 品項被規則判定為正餐型食物；咖啡、茶、飲料、甜點與點心不符合。
3. 交易具有精確發生時間。
4. 台北時間落在下列明確區間。

| 台北時間 | 自動餐別 |
|---|---|
| 05:00–10:59 | 早餐 |
| 11:00–14:59 | 午餐 |
| 17:00–21:59 | 晚餐 |
| 其他時間 | 不自動標記 |

自動標籤在回覆中顯示為 `午餐（自動）`。使用者明確寫 `晚餐` 或 `#晚餐` 時，以明確值為準，即使時間未知。明確餐別同時代表使用者在描述一筆食物消費：若沒有明確大分類，系統將大分類設為食物；若同時明確指定非食物分類，則視為衝突並拒絕整筆輸入。

`晚餐 200` 這種只有餐別詞與金額的自然輸入仍然合法：項目保存為「晚餐」，大分類為食物，餐別為明確晚餐。

### 5.3 自訂標籤

- 非保留 hashtag 視為自訂標籤，例如 `#約會 #台南`。
- 每筆最多 10 個自訂標籤。
- 每個標籤為 1–20 個 Unicode 字元，不含空白或 `#`。
- 同一帳本內以正規化後名稱判斷相同標籤；重複輸入只保存一次。
- 自訂標籤可以任意重疊，因此各標籤小計不能直接相加當作總支出。

範例：

```text
牛肉麵 150 #約會 #台北
→ 共同｜150 元｜食物・午餐（自動）・約會・台北
```

## 6. 日期與時間

系統分開保存消費日期與精確時間，以正確表達「知道昨天，但不知道幾點」。

### 6.1 支援格式

- 相對日期：`今天`、`昨天`、`前天`。
- 絕對日期：`YYYY/M/D`、`YYYY-MM-DD`。
- 時間：24 小時制 `HH:mm`。
- 不接受省略年份的 `M/D`，避免跨年猜錯。
- 日期、時間、餐別及範圍皆為前綴修飾詞，可交換順序且各最多一次。

相對日期一律以 LINE event timestamp 的台北日期為基準，不使用 webhook 收到或處理時間。

### 6.2 時間精度

| 輸入 | 消費日期 | 精確時間 | 自動餐別 |
|---|---|---|---|
| `牛肉麵 150` | LINE 事件日期 | LINE 事件時間 | 可推定 |
| `昨天 牛肉麵 150` | 昨天 | 未知 | 不推定 |
| `昨天 19:30 牛肉麵 150` | 昨天 | 19:30 | 可推定 |
| `昨天 晚餐 牛肉麵 150` | 昨天 | 未知 | 明確晚餐 |

只寫時間，例如 `19:30 牛肉麵 150`，代表今天 19:30。任何解析後晚於 LINE event timestamp 的日期時間均拒絕，因 MVP 只記錄已發生支出。

修改日期時保留原有精確時分；原本時間未知則保持未知。使用者可另用 `改 #編號 時間 未知` 清除時間。

## 7. 訊息契約

### 7.1 解析優先順序

為避免 `最近 5` 被誤記成 5 元支出，文字依下列順序解析：

1. 說明／分類等系統指令。
2. 查詢指令。
3. 修改／標籤指令。
4. 取消／還原指令。
5. 新增支出。

任何以保留指令詞開頭的無效指令都不得 fallback 成新增支出；應回覆該指令的格式錯誤。無法解析的文字也回覆一行簡短提示，避免純記帳群靜默漏帳；非文字訊息則忽略。

一則 LINE 訊息最多建立一筆交易。

### 7.2 新增（Create）

概念格式：

```text
[日期／時間／餐別／共同或個人前綴] <項目> <金額> [#標籤 ...]
```

規則：

- 項目去除前後空白後為 1–50 個字元。
- 金額固定 TWD、大於 0 的整數，位於訊息主體最後。
- 接受 `150`、`150元`、`$150`、`NT$150`、`1,200`，回覆統一顯示 `150 元`。
- `牛肉麵150` 也可解析為項目 `牛肉麵`、金額 150；若尾端數字語意不明則回覆要求確認，不猜測。
- 未指定範圍時使用共同。
- 明確系統標籤優先於自動判斷。
- 明確餐別在沒有明確大分類時會一併明確指定食物；明確非食物分類與餐別不得共存。
- 未來日期／時間、非法日期、零、負數、小數、重複衝突前綴或衝突系統標籤均不寫入。

成功回覆：

```text
已記帳 #K7M2Q9TX
共同｜牛肉麵｜150 元
標籤：食物・午餐（自動）・約會
時間：2026/08/13 12:10
付款：小明
```

日期已知、時間未知時顯示 `時間：2026/08/12（時間未指定）`。

### 7.3 查詢（Read）

| 指令 | 結果 |
|---|---|
| `查 #K7M2Q9TX` | 顯示完整資料與 active／已取消狀態 |
| `最近` | 最近輸入的 10 筆有效交易 |
| `最近 5` | 最近輸入的 5 筆；允許 1–20 |
| `今天`、`昨天` | 該消費日期的摘要 |
| `週報`、`這週`、`本週` | 週一到目前所屬週的支出摘要 |
| `上週` | 前一個週一到週日的支出摘要 |
| `本月` | 本月總額、共同小計、兩人的個人小計、大分類小計 |
| `月報` | `本月` 的別名 |
| `上月` | 前一個完整曆月的支出摘要 |
| `本月 共同` | 本月共同支出 |
| `本月 個人` | 操作者本月的個人支出 |
| `本月 #午餐` | 本月帶午餐標籤的支出 |
| `本月 #約會` | 本月帶約會標籤的支出 |
| `找 牛肉麵`、`搜尋 牛肉麵` | 項目名稱含關鍵字的最近 20 筆有效交易 |
| `排行`、`分類排行` | 本月大分類金額與占比排行 |

`最近` 按建立時間倒序，讓剛補登的舊帳仍容易找到；日／月列表按消費日期、精確時間倒序，時間未知者排在該日精確時間之後。

`本月`的總額每筆交易只加一次。標籤統計可重疊，回覆不得暗示自訂標籤小計相加等於總額。

精確查詢可以查看已取消交易；其他列表與統計預設排除已取消交易。

### 7.4 修改（Update）

一次指令只修改一種欄位：

```text
改 #K7M2Q9TX 項目 牛肉湯麵
改 #K7M2Q9TX 金額 180
改 #K7M2Q9TX 分類 交通
改 #K7M2Q9TX 分類 自動
改 #K7M2Q9TX 餐別 晚餐
改 #K7M2Q9TX 餐別 自動
改 #K7M2Q9TX 餐別 無
改 #K7M2Q9TX 範圍 個人
改 #K7M2Q9TX 付款人 小美
改 #K7M2Q9TX 所有人 小美
改 #K7M2Q9TX 日期 昨天
改 #K7M2Q9TX 時間 19:30
改 #K7M2Q9TX 時間 未知
```

標籤修改：

```text
加 #K7M2Q9TX 標籤 #約會 #台南
移除 #K7M2Q9TX 標籤 #台南
```

規則：

- 無效或無權修改具原子性：所有欄位保持不變，也不建立交易稽核事件。
- 已取消交易不能修改，必須先還原。
- 共同改個人時，未指定所有人則以操作者為所有人；個人改共同時清除所有人。
- 修改付款人不會自動更改個人所有人。
- 自動分類的交易修改項目後重新分類；明確分類保持不變。
- `分類 自動` 重新執行分類規則；`餐別 自動` 只有符合自動推定條件時才產生餐別。
- 分類變成非食物時清除餐別；明確餐別與非食物分類衝突時拒絕整次修改。
- 修改日期／時間後重新計算自動餐別，明確餐別保持不變。
- 修改後的日期時間若晚於該修改指令的 LINE event timestamp，整次修改原子拒絕；MVP 不保存未來支出。
- 成功時顯示修改前後值並保存 `updated` 稽核事件。

### 7.5 取消與還原（Delete／Restore）

```text
取消 #K7M2Q9TX
還原 #K7M2Q9TX
```

- 取消是軟刪除，交易變成 `voided`，不出現在一般列表與統計。
- 還原讓使用者取消的交易回到 `active`。
- 重複取消或重複還原具冪等性，不重複建立稽核事件。
- 共同交易兩人都可操作；個人交易只有所有人可操作。

### 7.6 說明與 onboarding

- Bot 加入允許的群組時，說明初始個人模式、共同模式切換及單筆明確 scope 格式。
- `說明`：顯示新增、查詢、修改、取消的常用範例。
- `分類`：列出大分類與餐別保留標籤。
- `標籤`：說明自訂 hashtag 用法。
- `幫助`、`help`：`說明`的別名。
- 說明、單筆、列表、期間摘要、搜尋與排行使用 LINE Flex Message；`altText` 保留完整純文字摘要供通知與不支援 Flex 的環境顯示。
- Flex 卡片只使用系統白名單元件與 message action，不接受任意 URI action；說明可使用最多三張 carousel bubble，其餘查詢使用單張 bubble。

### 7.7 第二位成員配對

- 已有一位 active member 的帳本，可由同一個允許群組內的第二位 LINE 使用者傳送完全匹配的 `配對` 自助加入。
- admission boundary 對尚未授權成員仍預設不保存 user ID 或訊息內容；唯一例外是正確群組內完全匹配的 `配對`，只保存到 worker 完成原子處理，完成後立即 redaction。
- 配對時鎖定 ledger 並重新檢查 active member 數必須恰好為一，避免兩位候選人同時成為第二位成員。
- 成功後第二位成員暫名為「另一半」，可立即新增、查詢與操作符合權限的帳目；重複傳送 `配對`只回覆已完成，不重複建立 member。
- 已有兩位 active member、非允許群組、非文字、缺少 user ID 或不是完全匹配的訊息，均不得成為配對入口。

## 8. LINE 原生事件

### 8.1 編輯訊息

LINE 原始新增訊息被編輯時，不自動修改既有帳目。若該 message ID 已建立交易，Bot 回覆：

```text
原帳目未變更；請使用「改 #K7M2Q9TX 欄位 新值」。
```

Bot 不解析編輯前後差異，只回覆泛用提示，也不保存編輯後的文字內容。

### 8.2 收回訊息

- 收回原始新增訊息時，刪除對應交易及其業務稽核內容，使它不再可查、不可統計、不可還原。
- 只保留不含品項、金額、標籤或成員資訊的 message ID tombstone 與收回時間，避免亂序重送重新建立。
- 收回修改、取消或還原指令不反轉已完成的帳務操作，也不保存該指令文字。
- Bot 先前已發到群組的確認訊息可能仍然可見；系統不能承諾從 LINE 群組中移除它。
- 線上 DB、inbox／outbox、log 與 error tracker 中的業務內容應立即清除。加密備份可能在既定保留期內仍含歷史版本；一般應用無法讀取。系統另維護與主要 DB recovery unit 分離、只含最小刪除 metadata 的 durable deletion journal；任何備份還原都必須先重放 journal 清除流程，才能重新開放服務。

`取消`用於保留紀錄但排除統計；LINE `收回`代表清除該筆帳目內容。

## 9. 非功能與安全需求

- 使用 LINE channel secret 對尚未 JSON parse 的原始 request bytes 驗證簽章；驗證失敗不解析、不寫入。
- 所有群組事件都必須來自設定的 group ID。文字 CRUD 等使用者操作另外要求 active member user ID；不保證帶 user ID 的 join／unsend 等群組生命週期事件只以 group ID 與 message 關聯驗證，否則可能無法完成 onboarding 或隱私清除。
- 每個 `webhookEventId` 只完成一次副作用；新增、修改、取消、還原、編輯與收回都具冪等性。
- 可靠 inbox 必須有處理狀態與重試策略，不能因登記事件後當機而永久漏帳。
- DB mutation 與 inbox 完成狀態在同一 transaction 中提交，或採能從 pending／failed 恢復的等價設計。
- 保存必要 outbound 狀態；DB 成功但 LINE 回覆 timeout 時，不得重複執行帳務副作用。MVP 只在 reply token 有效期內做 bounded retry，不自動改用 push fallback；若 token 過期則標記失敗並監控，接受極少數「帳已成功但確認未送達」，使用者可用 `最近` 核對。
- 所有瞬時時間用 PostgreSQL `timestamptz` 儲存；消費日期另存台北日曆日期。
- 金額使用整數最小貨幣單位，不使用浮點數。
- 公開交易編號至少 8 位 Base32／Base36，帳本內唯一且碰撞時重試。
- 一般新增與查詢從 webhook 到確認回覆的 p95 目標小於 5 秒。
- Channel secret、access token、DB 密碼只由 secret／環境變數提供；DB 使用 TLS 與最小權限帳號。
- 日誌、queue、error tracker 不記錄完整 webhook body、訊息文字、reply token、access token、channel secret 或完整簽章。
- request body 設定合理大小限制；備份需加密、設定保留期限並定期驗證可還原。message tombstone 與 durable deletion journal 的保留期不得短於最長備份保留期。

## 10. 成功指標

兩人試用一週後觀察：

- 解析成功率。
- 誤入帳率與格式錯誤率。
- 未分類率。
- 自動餐別修正／移除率。
- 取消率與還原率。
- p95 回覆時間與 webhook 重試率。

這些結果用來決定是否調整裸格式、標籤規則與餐別時段，而不是一開始引入不可解釋的 AI 猜測。
